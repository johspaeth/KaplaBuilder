# KaplaBuilder

Describe something ("an egg", "a bunny") in a chat, and say how many Kapla blocks
you have. KaplaBuilder gives you a **building plan that a real person can build**: a 3D
view and step-by-step instructions on a webpage. Lean 4 proves that the plan is safe to build.

Original design: [docs/DESIGN.md](docs/DESIGN.md) (it says which parts were built). Team
notes, not needed to understand the project: [docs/WORKSPLIT.md](docs/WORKSPLIT.md).

## What the plan guarantees (proven in Lean)

- It uses **at most N blocks**.
- It **stays standing after every step**, not only at the end.
- It stays standing **even if your hands are a bit imprecise**: each block may land up to
  1/2 of a block thickness (3.9 mm) from its planned spot, along `x` and along `y`.
- **Blocks fit where they go**: no gaps that a 3.9 mm error could close, no block dropped
  into a slot exactly its own width, and one block per step (the `hands` setting, default 1).

- **Every block touches the target, and every part of the target has a block**: at least
  one 1 × 1 × 1 cube per block and per bubble. The checker says yes exactly when this holds.
- Its **likeness score** is the score defined in `semantics/KaplaSemantics/Score.lean`, and is
  from 0 to 1. There is no minimum score: a person approves the design.

These two are proven in `semantics/` (statements and proofs:
[semantics/README.md](semantics/README.md)), but not yet checked by Comparator.

Not guaranteed (yet):

- Errors that **add up from level to level** (each block lined up against a block that is
  itself off). The 3.9 mm is measured from the plan, not from the block below.
- **Reaching** every block by hand: a block in a closed pocket only gets a warning
  ("may be hard to reach").
- **Turned blocks** (15°, 30°, 45°, 60°, 75°, ...): a plan with one is checked only at the
  planned positions. It is well-formed and stands after every step, but placement errors,
  gaps and reach are not checked. Such a plan is still "ok", and the physics notes say
  "at the planned positions only" (the report's `assurance` is `nominal`, not `robust`).
  `--robust-only` refuses it.
- **Pressing** a block down while placing it. We assume the builder sets it down and lets go.
- **Two supports of slightly different height**: a block on two separate stacks is checked
  as if both stacks had their planned height.
- **Sliding**: blocks never lean (turns are only about the vertical axis), so every contact
  is flat and friction is never needed (`stable_withFriction`).

The real-world failure modes (H1–H9), and which ones are proven, only warned about, or not
modelled, are in [DESIGN.md §2](docs/DESIGN.md#2-physical-feasibility-is-not-enough-the-human-model).

## How it works: an untrusted generator and a verified checker

```
 description (chat) ──► [Semantics: Claude] ──► target shape                (untrusted)
                                                   │
 N blocks, human model ─► [Planner: Claude] ──► plan                        (untrusted)
                                                   │
                          [Physics checker] ──► plan accepted or rejected   (VERIFIED)
                                                   │
                          [Scorer]          ──► score + fits the target     (VERIFIED)
                                                   │
                          [Web]             ──► webpage generated by Lean
```

The parts that search (Claude, the planner, and the solvers inside physics that look for
contact forces) are not trusted. They only *propose* a plan, or numbers that justify it
(for example the contact forces).
A small checker, with a proof that it is correct, accepts or rejects each proposal. A bug in
the search can make the result look worse. It cannot produce a plan that falls down.

Blocks are 15 × 3 × 1: one unit is one block thickness. All geometry uses exact fractions (`Rat`), never floats,
so the proofs are about the numbers the program really computes.

## Usage

```sh
lake exe kapla serve                                  # the website, http://localhost:8000
lake exe kapla check web/examples/house.json          # does this blueprint stand? exit 0 = ok
lake exe kapla view web/examples/house.json --out out/house   # write its webpage
lake exe kapla plan --strategy ai --blocks 20 --target semantics/fixtures/targets/egg.json
lake exe kapla gallery-check                          # are all gallery files good?
```

All commands and flags: [app/README.md](app/README.md). File formats: [web/README.md](web/README.md).

## Quick start

```sh
make install   # needs elan; builds everything with Lean 4.35 (pinned in lean-toolchain)
make run       # starts the website on http://localhost:8000
make check     # what CI checks (except `lake check` / `lake comparator`, Linux only)
```

Without an API key, the website still works: open a model from the **Gallery**, look at it
in 3D, and run the "stand-in tower" planner. The chat and the `ai` planners ask Claude and
need a key, in one of two places (the file wins):

```sh
cp .env.example .env            # then put your key in it (git ignores .env)
export ANTHROPIC_API_KEY=...    # or this
```

Also needed: `curl` (every call to Claude), and internet in the browser (the 3D view loads
three.js). The gallery's "Open a PR" button needs `git` and a logged-in `gh`.

## Layout: one folder per component

| Folder | Lean library | What it does | Owner | May import |
|---|---|---|---|---|
| `core/` | `KaplaCore` | shared types, JSON, basic geometry, engine interfaces, mocks | all (stewarded by D) | Lean core, Batteries |
| `physics/` | `KaplaPhysics` | does it stand, and can a human build it? (verified) | A | `KaplaCore`, `KaplaSpecs.PhysicsRules.*` |
| `semantics/` | `KaplaSemantics` | what to build (Claude), and how close are we? (verified checks and score) | B | `KaplaCore` |
| `planner/` | `KaplaPlanner` | which blocks go where, in which order (untrusted search) | C | `KaplaCore` |
| `web/` | `KaplaWeb` | webpage: 3D view, step cards, badges | D | `KaplaCore` |
| `app/` | `kapla` (exe) | the CLI; connects the real engines | D | everything |
| `specs/` | `KaplaSpecs` | theorem statements and the rules they are about, written and reviewed by humans | all | everything (`PhysicsRules/`: only `KaplaCore`) |
| `comparator/` | – | links each spec to its proof | all | – |

Work only in your own folder. Build only your part: `lake build KaplaPhysics`.
Every `.lean` file in your folder is built, even if nothing imports it, except files in a
`dev/` folder (`semantics/dev/`, `web/dev/`): those are tools for development, not built by CI.

## Rules for `main`

`main` is protected. You can merge only through a pull request, and only when the
**CI OK** check is green. Nobody can bypass this.

CI fails if:

1. **A build fails or warns.** Each library builds with `--fail-level=warning`.
   A `sorry` is a warning, so it fails.
2. **An import breaks the rules.** A component imports another component
   (`scripts/check_imports.sh`).
3. **A forbidden word appears** in code: `sorry`, `admit`, `axiom`, `native_decide`,
   `debug.skipKernelTC`, `maxHeartbeats 0`, `implemented_by`, `extern`, `unsafe`
   (`scripts/check_forbidden.sh`). This also counts words in comments.
4. **`lake check` fails.** The whole project is replayed through the Lean kernel, and only
   the standard axioms (`propext`, `Quot.sound`, `Classical.choice`) are allowed.

5. **`lake comparator` fails** for a file in `comparator/`: the proofs must prove exactly
   the statements in `specs/`. It runs in the same job as `lake check`, and can also be
   started on its own with the **Comparator** workflow (Actions → Comparator → Run workflow).

## How to work

1. Branch from `main`: `git switch -c physics/contacts`.
2. Change files in your folder. Run `lake build <YourLib>` often and `make check` before
   you push.
3. Unfinished proofs: keep the `sorry` on your branch. It cannot reach `main`.
4. Open a PR. Wait for **CI OK**. Merge.

## Specs and the comparator

A spec is a theorem statement that humans wrote and reviewed. It lives in `specs/`, with
`sorry` as its proof. The real proof lives in your folder, with **the same name and the same
statement**. A file in `comparator/` connects the two. Example: `specs/KaplaSpecs/Core.lean`,
`core/KaplaCore/Proofs.lean`, `comparator/core.json`.

To add a spec:

1. Write the statement in `specs/KaplaSpecs/<Component>.lean`. Import only the definitions it
   needs, not the proofs.
   If the statement is about rules that you would otherwise define in your folder (what
   "stable" means, for example), put those definitions in `specs/` too, so the meaning of
   the statement cannot change without a spec review. Example: `specs/KaplaSpecs/PhysicsRules/`.
2. Prove it in your folder, in a module that the spec does not import.
3. Add `comparator/<component>.json`: challenge module, solution module, theorem names.

Changes to `specs/`, `comparator/` and `core/` change what everyone relies on.
Get a review from the whole team before you merge them.

## What is trusted

- The Lean 4.35 kernel and the statements in `specs/` (and every definition they mention).
- No extra axioms. No `opaque` contracts yet. Add them here when you add them.
- **The Lean compiler.** The proofs are about the Lean definitions. When `kapla` runs, the
  checkers (`checkPlan`, `coreCheck`, ...) run as compiled code, not in the kernel.
- **The blueprint reader** in `app/Main.lean` (`readBuildPlan`, `ratOfJsonNumber`). It turns a
  JSON file into the `BuildPlan` that the physics engine checks. It has no proof.
- **The model reader** `KaplaSemantics.decode` (`semantics/KaplaSemantics/Json.lean`). It turns
  a model file into the `BubbleModel` that the scorer uses. It has `#guard` tests, no proof.
- **The viewer** (`KaplaWeb.parsePlan`, three.js in the browser). It reads the plan again, as
  `Float`s, only to draw it. A bug here shows a wrong picture; it does not change a verdict.
- **The web server** in `app/Main.lean` (`kapla serve`). It runs the physics check and the
  scorer again on every plan it shows, so a file or a planner cannot make a plan look safe.
- Not trusted, by design: **Claude** (chat and `ai` planners). Its answers are only proposals.
- **The physics model** (`spec/physics-rules.md`), most of all: planks are rigid and all the
  same (B1–B3); pushes at the corners of a patch can stand in for any spread-out push (F4);
  side, edge and corner touches carry no force (C3, C4); errors stay within R1.
